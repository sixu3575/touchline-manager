# 0.12.0 球员卡与观察知识

0.13.0所有公开能力和区间采用整数；中点评估也四舍五入，旧快照只取整展示。trainingProgress培养经验不发客户端、不参与能力评估或比赛。当前精度契约见[INTEGER_STATS.md](INTEGER_STATS.md)。

球员有三层数据：服务器真实30项能力 → 六项公开概览 → 教练/球探掌握的细项区间。比赛始终使用第一层。概览和评估既不写回能力，也不参与引擎的决策、质量、冲量或赛后评分。原六项skills继续是服务器的旧预算/评级缓存，新卡片不覆盖它。

## 公开概览

外场为速度、射门、传球、盘带、防守、身体；门将为扑救、接球、出球、反应、速度、选位。权重定义在assessment.mjs的CARD_GROUPS/KEEPER_CARD_GROUPS；它们是相关细项的加权、整数舍入摘要，不是六个新增竞技数值，也不改变原综合评级/身价/工资。没有复制FC素材、完整属性体系或专有规则。

## 观察与精度

| 条件 | 揭示规则 |
| --- | --- |
| 没有观察 | 所有细项待观察，概览公开 |
| 初步观察 stage1 | 按稳定属性顺序揭示约45%，区间宽32 |
| 持续观察 stage2 | 揭示约75%，区间宽16 |
| 深入评估 stage3 | 30项全部可评估，区间宽8 |
| Lv.5并累计至少8次观察 stage4 | 揭示精确值 |

默认教练Lv.2、球探Lv.1，最高5；下一等级升级费为等级×£25,000（一次性，没有另增周期工资）。只影响评估信息，不改善训练增幅或竞技能力。stage从1起，每两个团队等级增加一阶段，每四次观察增加一阶段，通常封顶3；达到Lv.5/8次才进入4。实际数值区间始终截到1–100，边缘可能更窄。

本队从开始追踪起每7个游戏日增加一次观察、每次合法全队训练增加一次；初始即有一次基础观察。签约保留已有球探次数，并从加入日起累计教练观察。外部球员每个游戏日只能观察一次，不消耗时间或资金；不能通过刷新/重复请求增加次数。球队可以在同一比赛日评估多名球员。本版没有球探行程、人员合同、专长和自动派遣。

属性揭示顺序和区间网格由私有存档种子、球员ID、属性键固定。更高阶段的已知区间嵌套收窄，升级不重新抽误差；真实能力成长跨过网格时，报告可随当前能力更新。报告并非对历史训练前数值的冻结估计。历史比赛快照按当前了解程度投影当时的真实能力；原事件、评分和轨迹不重新计算。旧档没有细项的历史快照不能据此还原真实小项。

## 隐藏边界

统一服务端投影player-view.mjs覆盖/api/state、所有动作成功和去重响应、/api/reports、/api/match-jobs及/api/state内任务。SSE继续只有索引和播放进度，二进制轨迹只有位置。原始attributes、技术生成模板、matchState、私有种子和事件动作质量/局部概率/心理调试值不发给浏览器；真实历史BLOB保留。仅CSS隐藏不合格。公开概览可供玩家推断大致特点，这是设计允许的信息，不承诺无法依据概览或比赛表现推测能力。

浏览器Player类型没有attributes。公开DTO的skills、potential、weakFoot是兼容界面的评估中点缓存，绝非服务器同名真实字段；未知细项按50估计。潜力/逆足界面显示区间或待观察，综合显示“评估综合”。名单排序、自动排阵预览/HTTP auto和训练推荐均用这份知识。服务器和AI对手原有的真实选人/比赛逻辑不改；新游戏初始首发属于预先给定阵容，不是教练能力报告。

## 持久化与回滚

JSON schema3新增可选assessment对象，内部version1：coach/scout等级与players[id]的joinedOn、sessions、visits、lastScouted。不增加SQL表、不重抽能力、不修改启动迁移。GET使用只读默认值；第一次合法管理动作或新比赛计划才创建知识。比赛计划在原日期追踪，再推进游戏日期；异步结算沿用原事务，跨季知识保留，换季新候选ID从未知开始。旧release能忽略可选对象，但回滚时应避免继续改动观察数据；完整回退以发布前备份为准。新动作仍必须通过原requestId/revision/事务和比赛锁。

没有改比赛算法；新增动作与持久数据、业务赛历观察接入需要完整业务赛季验证，使用明确测试报告，不重算未改变的物理比赛。属性核对见[ATTRIBUTE_AUDIT.md](ATTRIBUTE_AUDIT.md)；决策文档第9节新增知识图，不替换原六张竞技图。开发流程和审批约束保持原样。
